# Состояние сохранения и серверный контракт

Прогресс хранится в глобальном объекте `S`. Образец нового сохранения без персональных данных — [save-default.json](save-default.json). Поле `v:1` есть, но диспетчера миграций по версии нет. Описанный здесь API восстановлен по обращениям клиента; работающий сервер в переданном файле отсутствует.

## Совместимость обновления контента

Ключ `mintcoin_save_v1` и `v:1` сохранены. Новое поле `content` достраивается при загрузке, обновлении UI и сериализации. Отсутствующие или структурно некорректные `content`, `journey`, `sets` заменяются пустыми объектами. Это миграция нового блока, а не полная валидация сохранения: B05 и B06 остаются.

`content` содержит `version:1`, `journey` (id поручения → 1 после выдачи), `sets` (id набора → 1), `peakMinions` (максимум бригады, зафиксированный с момента обновления). Начальное значение — `{version:1,journey:{},sets:{},peakMinions:0}`. Для старого сохранения учитывается текущая бригада; её размер в прежних уже сброшенных забегах восстановить нельзя.

Выдача сначала проверяет условия, ставит отметку, начисляет валюты и вызывает `saveAll(true)`. Престиж сохраняет блок, полный сброс очищает. Остальные цели используют существующие пожизненные счётчики, поэтому старый игрок может забрать уже выполненные вехи по очереди. Клиентские отметки не являются серверной защитой от подмены сохранения или конфликтов между устройствами.

## Режим сборки без сервера

Параметр `CONFIG.STANDALONE` не является частью сохранения. В рабочей демо-игре он равен `false`; `build-telegram.cjs` задаёт `true` в отдельной сборке. В таком режиме не отправляются hello/invoice/claim, не показываются предложения за Stars, реклама и кнопка удвоения офлайна; экран приглашений не обещает реферальную награду. Доступны основной игровой цикл, покупки за игровые кристаллы, базовый офлайн и существующее хранение. Серверные методы дополнительно закрыты на уровне функций.

## Текущий забег

| Поле run | Значение |
|---|---|
| zone | Текущая зона, от 1 |
| bought | Счётчик покупок монет для роста цены |
| minions | Число миньонов |
| upg | Объект уровней улучшений по id |
| coins | Массив тиров, переносится из мира при сериализации |
| earned | Все деньги, заработанные в этом забеге |
| started | Время создания забега |

Задание в `quests.list`: `{id,t,goal,p,g,c}` — тип, готовый текст, цель, прогресс, gems, флаг получения. Тексты сохраняются в JSON и впоследствии вставляются в HTML. Это дополнительная причина валидировать загружаемые данные.

## Локальное хранение

Ключ: `mintcoin_save_v1`. JSON не шифруется и не подписывается. `serialize()` имеет побочный эффект: обновляет `run.coins`, `lastSeen` и `savedAt`. Поэтому его нельзя использовать как нейтральный метод просмотра без изменения времени прогресса.

`saveAll(force)` всегда сохраняет локально, а в облако — если прошло больше 45 секунд либо `force=true`. На обычном цикле вызов идёт каждые более 15 секунд накопленного `dt`; также при скрытии страницы, `pagehide`, переезде, престиже, выдаче покупки и ряде наград. Покупки за обычные деньги, простые броски, настройки и выбор шляпы преимущественно ждут автосохранения. `saveLocal` объявлен, но основной путь — `saveAll`.

Ошибки localStorage проглатываются. Пользователь не узнает о переполнении или запрете хранилища. Ключ не содержит Telegram user id: два аккаунта на одном браузерном origin потенциально разделяют локальный прогресс. Отдельные origin, напротив, автоматически не переносят его.

`mergeLoaded(o)` добавляет отсутствующие верхнеуровневые поля и недостающие ключи stats/settings. Он не проверяет диапазоны, типы, вложенные поля run/daily/quests, целостность массивов и допустимость версии. `stats:null` вызывает TypeError; отрицательные валюты и тир 99 принимаются. Непарсящийся JSON localStorage превращается в отсутствие сохранения, но структурно повреждённый валидный JSON может сорвать boot.

## CloudStorage

Условия доступности: определён Telegram WebApp, непустой `initData`, наличие CloudStorage и `isVersionAtLeast('6.9')`. Сериализованная строка режется по 3900 символов, пишется в `s0`, `s1`, …, число частей — в `sn`. В документации Telegram CloudStorage допускает до 4096 символов на значение; сохранение отделено по пользователю и боту. [Telegram CloudStorage](https://core.telegram.org/bots/webapps#cloudstorage).

В клиенте нет подтверждения всех записей до обновления `sn`, номера поколения, checksum, чтения назад и повторной отправки после ошибки. Старые лишние части не удаляются. Один неуспешный или перемешанный chunk может привести к невалидному JSON либо смешанному состоянию. Это структурный риск алгоритма; настоящая сеть CloudStorage в проверках не участвовала.

Загрузка ждёт облако до 2,5 секунды. Более поздний ответ игнорируется. При конфликте побеждает больший клиентский `savedAt`, поэтому часы устройства влияют на выбор. Нет merge по ресурсам, серверной ревизии, защиты нескольких устройств или нескольких открытых окон. Выбранное повреждённое сохранение не откатывается к альтернативе после ошибки boot.

## Офлайн как транзакция

Сейчас вычисленная награда существует только в замыкании обработчиков модалки. Её нет в `S` и неоткуда восстановить после закрытия/замены модалки. Нажатие ×2 сначала закрывает окно, затем запускает рекламу. Лимит, недоступность или отказ не возвращают базовую сумму. Автосохранение тем временем продвигает `lastSeen`.

Предлагаемая будущая модель: сохранить `pendingOffline` с идентификатором периода и базовой суммой до показа, отдельно хранить факт выплаты/удвоения, при неуспехе рекламы оставлять возможность взять базу, делать получение идемпотентным. Это предложение исправления; в текущем клиенте таких полей нет.

`window.APP_CONFIG` перекрывает значения до запуска логики. Пустые строки пропускаются, кроме `API_BASE`; whitelist ключей нет. Никакой загрузчик отдельного config-файла не подключён — его ещё надо добавить либо подставить значения при выпуске.

## Фактический API клиента

Все запросы — `POST`, `Content-Type: application/json`, заголовок `X-Init-Data` содержит сырую строку Telegram initData. В браузерном гостевом режиме строка пустая. `fetch` принимает JSON только при успешном HTTP-статусе. Нет общего timeout, AbortController, схем ответа и общей retry-политики.

| Endpoint | Тело | Ожидаемый ответ | Использование |
|---|---|---|---|
| `/api/hello` | `{ref: string|null}` | Любой корректный JSON, содержимое игнорируется | Регистрация входа и передача реферала в boot |
| `/api/invoice` | `{sku: string}` | `{link: string}` | URL для `Telegram.WebApp.openInvoice` |
| `/api/claim` | `{}` | См. ниже | Подтверждённые права, выдачи, реферальные gems |

Пример структуры, выведенный из клиента, а не ответ существующего сервера:

```json
{
  "clubUntil": 1791676800000,
  "purchases": ["vip", "x2forever", "starter"],
  "grants": [{"sku": "gems_s"}, {"sku": "club", "subUntil": 1791676800000}],
  "refGems": 30
}
```

`clubUntil` в claim назначается только если truthy; ноль не отзовёт клуб. `purchases` только добавляет права, не удаляет их. `grants` выдаются последовательно через `Pay.grant`, но у клиента нет журнала grant id. `refGems` прибавляется каждый раз при truthy значении. Неизвестные SKU в `grant` игнорируются. Количество gems берётся из клиентского каталога, а не из отдельного amount ответа.

После статуса invoice `paid` запускается claim: первая попытка через 800 мс, затем до шести попыток с промежутком 1500 мс, пока не появится хотя бы один grant. При `failed` показывается ошибка. Для pending/cancelled специальной обработки нет. При входе claim выполняется независимо от hello, что требует учесть гонку создания реферальной награды.

Изменение `purchases`, `clubUntil` или `refGems` само по себе в claim не вызывает сохранение. Сохранение происходит внутри grant и периодически. Если grants нет, подтверждённая сервером выдача может остаться только в памяти до следующего save.

## Контракт будущего сервера

Это проектные требования, а не описание реализованных компонентов.

1. Проверять подлинность и срок initData на сервере; не считать `initDataUnsafe.user` авторизацией. Официальный способ валидации описан у Telegram. [Валидация Mini Apps](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).
2. Хранить серверный каталог, заказы, полученные платежи, постоянные права, выдачи и рефералы. Сервер определяет цену и SKU, клиент не сообщает доверенную сумму.
3. Создавать invoice, принимать webhook и выдавать покупку только после серверного `successful_payment`; для цифровых товаров используется XTR. Хранить идентификатор платежа, поддержать `/paysupport` и возвраты. [Telegram Stars](https://core.telegram.org/bots/payments-stars).
4. Ввести уникальные grant id, устойчивую выдачу и подтверждение применения либо серверный авторитетный баланс. Однократное удаление grant при чтении без подтверждения создаёт риск потери; повторный ответ без клиентской защиты создаёт дубли.
5. Определить семантику восстановления starter: постоянная шляпа должна восстанавливаться отдельно от одноразового начисления 300 gems/100 tokens. Продумать возврат и отзыв прав; текущий аддитивный claim этого не выражает.
6. Уточнить клуб: разовые 30 дней или настоящая возобновляемая подписка. Надпись `/мес` и `sub:true` не доказывают реализацию рекуррентных списаний.
7. Для рефералов валидировать `ref_<id>`, исключить самоприглашение и повторную привязку, связать выдачу с пользователем и событием.

При отдельном домене API понадобятся обработка preflight и CORS для `Content-Type` и `X-Init-Data`. При одном origin этот дополнительный механизм не нужен. Секрет бота должен оставаться только на сервере.
